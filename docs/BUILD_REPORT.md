## Decisions

### Python over C++
The machine had Python 3.13.3 with numpy and numba, Visual Studio 2022, and an NVIDIA Quadro RTX 3000 (OpenGL 3.3). Python won for three reasons:
- **Iteration speed.** There is no build step. A change can be tested seconds after it is written, and a one-hour budget is dominated by how many test-and-fix cycles fit in it.
- **numba covers the slow parts.** The only code that has to be fast in a voxel game is terrain generation, lighting and meshing. numba compiles those functions to machine code; with `nogil=True`, several of them can run on worker threads at the same time. After compiling, a 16×128×16 chunk generates in about 1.3 ms and lights and meshes in about 6.7 ms on one thread.
- **Small, well-known libraries.** moderngl provides modern OpenGL (shaders, vertex buffers) with little boilerplate. pygame-ce provides the window, input, audio mixer and fonts. Both are single pip wheels; nothing else had to be installed.

C++ would render faster and have no startup compile, but setting up OpenGL, windowing and audio without a package manager would have used a large share of the hour.

### No asset files
Shipping Minecraft's textures or sounds was not an option. Instead:
- `textures.py` paints a 256×256 atlas of 16×16 pixel-art tiles with numpy from a fixed random seed, so the look is the same on every run.
- The `Sounds` class synthesizes every sound effect from filtered noise and tones when the game starts.

The game is self-contained and has no licensing questions.

### Scope order
Features were added in the order a Minecraft player would notice their absence:
1. The world, lighting and sky.
2. Building and movement.
3. Animals, then survival mode.
4. Hostile mobs.
5. Polish.

Each round ended with the game in a working, tested state, so stopping at any point would still have left a complete game.

### Engine layout
- **`engine.py`** holds everything numba compiles: the block table, Perlin noise, terrain generation, flood-fill lighting and the chunk mesher. It has no OpenGL or pygame code.
- **`textures.py`** builds the texture atlas.
- **`stelexcraft.py`** holds the rest of the game:
  - world streaming and rendering;
  - the player, mobs and physics;
  - sound, user interface, survival rules and saving;
  - the scripted test mode.

## How it was tested

Nobody played StelexCraft during the build. All testing was automated or visual:
- **Scripted test mode.** Setting the environment variable `STELEX_AUTOTEST` to a folder makes the game play itself for 16 seconds and then exit. It writes four screenshots (`shot0.png` to `shot3.png`) and its own save file (`test.sav`) into that folder, leaving `world.sav` alone. Along the way it:
  - places a torch;
  - starts rain and sets off TNT;
  - flies to a lava pool in a cave;
  - generates a new world and switches to survival;
  - takes damage, kills an animal, breaks and places blocks, spawns item drops and starts mining;
  - sets off TNT again, crafts, and opens the inventory.

  The scenario changed as features were added, so each run exercised the newest code.
- **Visual checks.** After each change, the screenshots were opened and inspected: geometry, lighting, the user interface, and whether new features appeared as intended. This caught several issues that were not crashes: the oversized arm, spawning on treetops, and smoke that was too heavy.
- **Crash checks.** Every run's console output was checked for Python tracebacks, and there were several normal launches without the test mode.
- **Static checks.** pyflakes found no problems.
- **Save and load.** Two consecutive runs confirmed that world edits and the player's position persist. Each later test run also loaded the previous run's save.

To repeat the test run:
```
# PowerShell
$env:STELEX_AUTOTEST = "C:\some\empty\folder"; python stelexcraft.py; Remove-Item Env:STELEX_AUTOTEST
# bash
STELEX_AUTOTEST=/some/empty/folder python stelexcraft.py
```
When the variable is not set, the test code does nothing.

What automated testing cannot tell you is how the game feels: mouse response, movement, difficulty, and whether anything is confusing. Those still need a human player.

## Problems found and fixed

| Problem | Cause | Fix |
| --- | --- | --- |
| The first engine benchmark printed nothing | Output buffering, plus a stray `cat` in the shell command | Re-ran with flushed output |
| Missing `OBSIDIAN_ID` constant | The game referenced a constant the engine didn't define | Added it to `engine.py` before the first launch |
| Frame rate locked at 30 | Primary monitor runs at 30 Hz; vsync waited for it | Vsync off, 144 FPS cap |
| 28 FPS with a few animals | Mob models built vertex by vertex in Python | Built with numpy array operations instead |
| `KeyError: 'steve'` in third person | The player model went through the animal model lookup | Sent the player model to the humanoid builder |
| Test crash on a new world | The test script placed torches before the new world's chunks existed | Guarded the test scenario (the game itself was fine) |
| Crash waiting to happen with torch smoke | Smoke particles have one more field than other particles, and the particle loop unpacked a fixed number | Fixed before it shipped |
| Spawning on top of trees | Spawn used the highest solid block, which could be leaves | Spawn picks a nearby column whose top is not a tree |
| Bare arm too large and pointing oddly | First guess at the transform | Reshaped to rise from the bottom right, as in Minecraft |
| Torch smoke too large and opaque | First guess at size and opacity | Smaller, fading, partly transparent puffs |
| One code patch didn't apply | Its search text matched in more than one place | Every patch script refuses to write unless its search text matches exactly once, so the file was untouched; retried with a unique anchor |
| Shell heredocs failed with quoting errors | Bash on Windows mis-parsed some long heredocs | Wrote patch scripts to files first |
| Some test screenshots showed the pause menu | The game pauses when its window loses focus, as Minecraft does | Expected behavior; no fix needed |

## Reflections

- **What worked.**
  - Python with numba was fast enough at runtime and much faster to develop in.
  - The scripted test mode with screenshot checks was the most valuable tool of the session. It turned "does it work?" into a 20-second loop.
  - Keeping the game shippable at the end of every round meant the extensions added features rather than risk.
- **What it cost.**
  - Python's per-frame overhead (about 7 ms of CPU) limits how many entities and particles the game can draw.
  - The first launch has a one-time compile of about 15 seconds while numba builds the engine.
- **What is still unknown.** How Minecraft players will rate the feel of movement, mining and combat. The movement constants were copied from Minecraft's documented values (see [COMPARISON.md](COMPARISON.md)), but they haven't been checked against real play.
